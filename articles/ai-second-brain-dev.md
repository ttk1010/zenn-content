## 「初日で5,000行」その後が本題

個人開発で **AI Second Brain**（わかりにくい概念やニュースをイラスト付きノートにして貯めるツール）を作りました。開発はほぼ **Claude Code に“リードエンジニア”をやらせた**のですが、スピードがなかなかのものでした。

- 初日：**+5,067行 / 75ファイル / 11コミット**（データモデルからVault保存まで一式）
- 2日目まで：**+8,282行**（CLI疎通＋イラスト・ニュース取り込み）
- **4日目に v0.1.0 を公開**
- 通算：72コミット / 11本のADR / Python約7,280行

ただ、この記事で伝えたいのは「速い」ことではありません。**AIエージェントに任せると速い代わりに"荒れ"がち**——命名も設計もバラバラ、なぜそうしたか誰も覚えていない、という状態になりやすい。そこを、**"型"で崩さずに済ませた**話が本題です。[前回の紹介記事](https://zenn.dev/ttk1010/articles/ai-second-brain-intro)の続編として、その開発手法をまとめます。

リポジトリは公開しています：[ttk1010/ai-second-brain](https://github.com/ttk1010/ai-second-brain)。ADRもIssueも全部読めるので、この記事の"型"を実物で追体験できます。

## 何を作ったのか

入力（概念・ニュースURL・比較）を **Knowledge Object** という1つのデータ構造に正規化し、そこからMarkdownノートもイラストも生成する——という設計のツールです。詳細は前回記事に譲り、ここでは「**どう作ったか**」に集中します。

## 体制：Claudeがリードエンジニア、人間はプロダクトオーナー

最初に `CLAUDE.md`（リポジトリ直下の指示書）で役割と規律を固定しました。ここが全ての土台です。

- **Claude Code = リードエンジニア**：アーキテクチャ・実装・テスト・ドキュメント・リポジトリ整備を担う
- **人間 = プロダクトオーナー**：ゴールと方針を決める。**プロダクトの意思決定は勝手に変えさせない**
- **優先順位を明文化**：単純さ > 読みやすさ > 保守性 > 拡張性 > 性能
- **ワークフローを固定**：Issueを読む → 実装計画を出す → 承認 → 実装 → テスト → 変更要約 → コミット

「速く書ける」だけのAIを、「**保守可能な方向に速く走る**」AIに変える。そのためのルールブックが `CLAUDE.md` です。

## 型①：Issue駆動 + CI で“荒れ”を防ぐ

思いつきで実装させず、必ずIssueを起点にしました。

1. `.github/issues/NN-*.md` に背景・ゴール・Open questions・完了条件を書く
2. `gh` コマンドでGitHub Issue化
3. アプリコードに触るときだけ**ブランチを切る**（ドキュメントはmain直push）
4. PRを作り、**GitHub ActionsでCI（ruff + pytest）**
5. **squashマージ**して1 Issue = 1コミットに畳む

この「小さく出してCIを通す」ループのおかげで、爆速でも各コミットが検証済み・レビュー可能な状態を保てました。テストは現在42ファイル。**AIに自分の成果を毎回検証させる**のが、荒れ防止の一番の効きどころでした。

## 型②：ADRで「なぜ」を残す — セッションを跨ぐ記憶

一番効いたのが **ADR（Architecture Decision Record）** です。設計判断のたびに「文脈・決定・却下した代替案」を `docs/adr/` に1ファイル残す。現在11本あります。

これは単なる几帳面さではありません。**AIエージェントはセッションが変わると記憶を失う**からです。実際、Vaultのパスを日本語からASCIIに変えた拍子に環境が壊れ、作業セッションが継続できなくなったことがありました。それでも**ADRとIssueに意図が残っていたおかげで、新しいセッションが文脈を読み直してそのまま開発を再開**できました。「なぜこの設計か」を人間の記憶ではなくリポジトリに置くことで、AI主体の開発でも一貫性が続きます。

## 型③：フェーズで小さく出す

大きく作らず、動くものを小刻みに公開しました。

| フェーズ | 内容 |
| --- | --- |
| Phase 1 | 基盤（KOモデル・分類・抽出・Markdown・Vault・CLI） |
| Phase 2 | イラスト生成＋ニュース取り込み |
| Phase 3 | 知識の整理（Vaultリンカー＋`asb-relink`スキル） |
| Phase 4 | 自動化（Inboxキュー＋Telegram連携） |
| 以降 | 比較タイプ・ドメイン非依存化・生成時ガイダンス・ログイン必須サイト取り込み・月次ダイジェスト… |

各フェーズはマイルストーンとして管理し、単発の改善は独立Issueに。**「大きな正解」を狙わず、小さな改善を積む**方針（これも`CLAUDE.md`に明記）が、AIとの共同開発では特に相性が良いと感じました。

## この“型”はテンプレートとして公開しています

ここまでの型①〜③は、特定のプロダクトに依存しません。そこで **AI Second Brainの開発から抽出して、再利用できるテンプレート集 [dev-playbook](https://github.com/ttk1010/dev-playbook) として公開**しました。Issue駆動のワークフロー（`WORKFLOW.md`）、AIエージェントへの指示のコツ、`CLAUDE.md`・Issue・ADRの雛形が入っています。GitHubのテンプレートリポジトリにしてあるので、新しいプロジェクトにコピーすれば、同じやり方ですぐに始められます。この記事の"型"を、そのまま持ち帰れる形にしたものです。

## ハマりどころと学び

もちろん、すべてがスムーズに進んだわけではありません。AIエージェントとの開発ならではの詰まりどころもいくつかありました。

- **「画面には出るのに、取れないデータ」問題**：月次ダイジェストで使うニュースサイトのランキングは、ブラウザには表示されるのに、プログラムから取得しようとすると中身が空でした（データがページの裏側に隠れて持たれている状態）。ここは思い込みで実装させず、**まず本物のデータで「どこに何があるか」を確かめる**調査をClaudeと何度も往復し、ようやく安定して取り出せるように。AIに書かせる前に"現物確認"を挟むと、手戻りが一気に減りました。
- **イラストが要点を捉えない問題**：ダイジェスト画像のラベルが、記事タイトルを機械的に短くしただけで内容を表せていませんでした。**記事本文をClaudeに読ませて、核心の言葉を含む短いラベルを書かせる**方式に変えて解決。人間が「ここが違う」と返す→AIが直す、の往復が効きました。
- **お金の設計は人間が主導**：同じ入力の作り直しは自動でスキップ（冪等）、画像を省くオプション、固定費ゼロのローカル運用——**コストの勘所はAI任せにせず人間が決める**べき領域でした。

学びを一言でいうと、**AIエージェントは"実行力"は高いが、"一貫性"や"現実との突き合わせ"は仕組みと人間で支える必要がある**、ということでした。

## まとめ：AIに“保守可能な”開発をさせる勘所

- **憲章**（`CLAUDE.md`）で役割・優先順位・ワークフローを固定する
- **Issue駆動＋CI**で、速くても検証済み・レビュー可能に保つ
- **ADR**で「なぜ」を残し、セッションを跨いでも文脈を継続させる
- **フェーズ**で小さく出す。大正解より小改善
- **意思決定と品質の最終責任は人間**（プロダクトオーナー）が持つ

この型さえ敷けば、AIエージェント主体でも「速いのに崩れない」開発は十分に現実的でした。型そのものは前述の [dev-playbook](https://github.com/ttk1010/dev-playbook) にまとめてあるので、よければ持ち帰って試してみてください。
